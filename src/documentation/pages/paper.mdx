  <section class="paper-abstract" aria-labelledby="paper-abstract">
    <h2 id="paper-abstract">Abstract</h2>
    <p>Coding agents write interface code faster than a person can review it, and every change risks an invariant nobody wrote down. Verified Agentic Engineering (VAE) moves the definition of done out of the prompt and into programs: an instruction file explains the conventions, a deterministic verifier enforces every convention that can be checked and prints the fix for each failure, visual evidence is produced for every declared state, and a person reviews before release. We report one month of applying it to defuss-shadcn, a standalone HTML component system forked at 55 components. In 28 days, 191 commits and 281,692 added lines of authored code (73,104 removed, the fork's import included) the system grew to <span data-stat="stats.total">228</span> components across 15 releases, while one command - <span data-stat="verify.gates">78</span> gates in <span data-stat="verify.seconds" data-stat-format="s">10.2</span> s - kept it consistent. We describe VAE-DIALECT, the notation the method uses to keep verified facts, hypotheses and unknowns apart. We also report what the gates did not catch: a build that froze the maintainer's machine, an animation timing bug, a growth claim the data did not support. The last section is the position of the agent that wrote this report.</p>
  </section>

  <section class="paper-section" aria-labelledby="paper-s1">
    <h2 id="paper-s1"><span class="paper-num">1</span>Introduction</h2>
    <p>A prompt can ask an agent to run the tests, to mock nothing and to remove its debug output. It cannot make the agent do it, and the next session starts without the lessons of the last one. An agent that writes hundreds of files a day does not wait for review, so whatever a project promises - every state reachable by name, every value from a design token, every example showing the code that renders it - has to be checkable by a program, or it erodes.</p>
    <p>VAE is a response to that. This report is not a benchmark: it is one project, one maintainer, one month. Its value is that everything in it can be checked. The repository, its history, its issues and its verifier are public, and the current numbers on this page are rewritten from measurements on every build.</p>
  </section>

  <section class="paper-section" aria-labelledby="paper-s2">
    <h2 id="paper-s2"><span class="paper-num">2</span>The method</h2>
    <p>VAE, as packaged in <a href="https://github.com/kyr0/defuss-vae" target="_blank" rel="noopener">defuss-vae</a>, has five human-triggered skills - plan, implement, review, docs, finalize - and small stdlib-only programs that verify, gate and remember. The agent does the work; programs decide whether the work is done.</p>
    <h3 id="paper-s2-1">2.1 Programs, not prompts</h3>
    <p>Hooks deny <code>git commit</code> until the exact code fingerprint has passed verify, review and docs, and send the agent back when it tries to stop early. The gate fails closed: a missing command, a missing metric or a crashing check blocks instead of waving the change through. Tests use real subsystems instead of mocks; end-to-end tests consume the built artifact and must leave fresh output. A check that cannot fail is not evidence - the defuss-vae notes record that plain <code>oxlint</code> exits 0 on findings, which is why every lint call carries <code>--deny-warnings</code>.</p>
    <h3 id="paper-s2-2">2.2 Memory that is loaded</h3>
    <p>Failures become episodes; recurring ones become tests or verifier rules; durable decisions go into a short memory file that the harness injects into every new session. Lessons are ranked by strength: <strong>an executable check &gt; a memory line &gt; an episode line</strong>. The strongest form of a lesson is one a program enforces, because a model forgets and a gate does not.</p>
  </section>

  <section class="paper-section" aria-labelledby="paper-s3">
    <h2 id="paper-s3"><span class="paper-num">3</span>VAE-DIALECT</h2>
    <p>VAE-DIALECT is a superset of technical English for agent output and for the skills' own prompts: fewer tokens, still uniquely decodable. Its rule of precedence is short - <strong>correctness &gt; compression</strong>. Its core is three epistemic tags that never mix:</p>
    <ul class="paper-findings paper-tags">
      <li><span class="paper-tag" data-tag="verified">VERIFIED[scope]</span> Established by direct inspection, command output, a test, a measurement or a named authoritative source. Evidence older than the last relevant edit is stale.</li>
      <li><span class="paper-tag" data-tag="hypothesis">HYPOTHESIS[scope]</span> A testable inference, not yet established - with the cheapest discriminating test or falsifier when it matters.</li>
      <li><span class="paper-tag" data-tag="unknown">UNKNOWN[scope]</span> A material fact the available evidence does not establish - naming the missing evidence. <code>P=?</code> marks an unknown value.</li>
    </ul>
    <p>Confidence language never promotes a hypothesis. On top of the tags, a small operator grammar replaces whole phrases. Operators are exact uppercase words; any other uppercase is forbidden, so an operator is never ambiguous:</p>
    <figure class="paper-table">
      <table class="table">
        <thead><tr><th scope="col">Write</th><th scope="col">Means</th></tr></thead>
        <tbody>
          <tr><td><code>IF A THEN B ELSE C</code></td><td>Implication; <code>ELSE</code> binds to the nearest <code>IF</code></td></tr>
          <tr><td><code>A WHEN B</code></td><td>Equivalence of complete propositions - never a condition</td></tr>
          <tr><td><code>a → b → c</code></td><td>A sequence or a ladder: try in order, stop at the first rung that holds; <code>cmd → result</code> is observed output</td></tr>
          <tr><td><code>A CAUSES B</code> · <code>P BC E</code> · <code>X SAYS P</code></td><td>Causality · evidence or reason · attribution</td></tr>
          <tr><td><code>EVERY</code> · <code>SOME</code> · <code>ONE</code></td><td>∀ · ∃ · ∃!</td></tr>
          <tr><td><code>A REQUIRES B</code> · <code>MAY</code></td><td>B is necessary for A · permitted or possible</td></tr>
          <tr><td><code>A &gt; B</code> · <code>a|b</code> · <code>∅</code></td><td>A outranks B · alternatives for one slot · none</td></tr>
        </tbody>
      </table>
      <figcaption class="paper-table-caption"><b>Table 1.</b> The VAE-DIALECT operators (abridged from the canonical spec in defuss-vae). Code, commands, paths and quotations are never compressed.</figcaption>
    </figure>
    <p>Its losslessness rule is what makes it more than shorthand: before emitting compressed text, the writer expands it mentally; if the expansion is not unique, or loses more than negligible meaning, the shortest longer form that is unique is used instead. A report in the dialect reads like this:</p>
    <pre class="paper-code"><code>VERIFIED[bundle] BC `bun tests/e2e/scaffold-lean.e2e.ts` → 6/6 apps render as on all.css + all.js
HYPOTHESIS[leak] BC heap +36 MB/page after module release; falsifier=close each happy-dom window, re-measure
UNKNOWN[scaffold-time] BC no timestamps in this repo for the prompts that built the scaffolds
IF HYPOTHESIS[leak] THEN next=cap heap at 4 GB, probe ELSE next=bisect plugins</code></pre>
  </section>

  <section class="paper-section" aria-labelledby="paper-s4">
    <h2 id="paper-s4"><span class="paper-num">4</span>The case: defuss-shadcn</h2>
    <p>defuss-shadcn is a component system of semantic HTML, modern CSS and plain JavaScript on shadcn/ui's design tokens: no framework, no build step for consumers. It was forked from codylindley/shadcn-html, which had 55 component folders when its development stopped in April 2026. The fork's first commit is dated 2026-09-05.</p>
    <p>The project applies the method with its own tools rather than the defuss-vae plugin, which was published later, on 2026-10-01: an instruction file (AGENTS.md) and a verifier (<code>scripts/verify.ts</code>) that runs at the end of every build. Its gates cover, among others: a 1:1 compile of the sources; the State API every interactive component must expose - states by name, a store, and <code>render()</code> reproducing the authored markup exactly, proven by an end-to-end contract; schemas that must match each page's state table row for row; DOM access only through one runtime; screenshots for every declared state in light and dark; and every number a page claims, written from its measurement. The same rules run on these very pages.</p>
  </section>

    <h3 id="paper-s5-2">5.2 Review load</h3>
    <p><span class="paper-tag" data-tag="verified">VERIFIED</span> On 2026-09-07 the maintainer reviewed the documentation site by hand and filed 52 issues in about eight hours - wrong corners, missing examples, unannounced field hints, dead links. 18 were closed within twelve hours; the fix commits name their issues (<code>fix(select): … (issue #32)</code>). The remaining ones were closed in one batch on 2026-09-28, so for those the close date is an upper bound, not the fix date.</p>
    <p>That sweep is the human review the method budgets for: one person reading what the gates cannot judge - whether a corner looks right - instead of re-checking what they can. <span class="paper-tag" data-tag="hypothesis">HYPOTHESIS</span> the review effort per component falls as the gates grow, because each class of defect found by hand becomes a gate; falsifier: issue counts per new component that do not fall across sweeps. One sweep is not enough data to say.</p>

    <h3 id="paper-s5-4">5.4 Generation speed</h3>
    <p><span class="paper-tag" data-tag="verified">VERIFIED</span> Aron Homberg SAYS each of the six application scaffolds took about 15 minutes to generate and was driven by a prompt of five to ten sentences. <span class="paper-tag" data-tag="unknown">UNKNOWN</span> for this report: the repository holds no timestamps of those prompts, so the figure is the maintainer's account, not a measurement. What the repository does show is that each scaffold passes the same gates as hand-reviewed components, its own interaction e2e, and the lean-bundle equivalence test.</p>
    <p><span class="paper-tag" data-tag="hypothesis">HYPOTHESIS</span> current frontier models build such applications quickly <em>because</em> the system gives them good examples (every component page is executable documentation) and clear instructions (a skill per component), and because the gate turns their mistakes into fix lines instead of silent drift. Falsifier: the same prompts against the same models without the component skills and without the verifier, timed and gated the same way. We have not run that comparison.</p>
  </section>

  <section class="paper-section" aria-labelledby="paper-s6">
    <h2 id="paper-s6"><span class="paper-num">6</span>Self-correction in practice</h2>
    <p>The most useful thing a gate does is not to fail - it is to make the agent's next step obvious. Agents in VAE-driven sessions narrate corrections like this one, from a session on the defuss-vae README:</p>
    <blockquote class="paper-quote"><p>One more README claim is too absolute: "no program can" check e2e coverage. Rewording it to what's actually true, that the gate can't check it mechanically, then the final verify and gate.</p></blockquote>
    <p>Nothing forced that sentence: the check that would fail on it does not exist. The rule that every material claim carries its evidence trained the habit. From the session that wrote this report, each with its evidence:</p>
    <ul class="paper-findings">
      <li><strong>The lean bundles were wrong first.</strong> The test comparing each app on its own bundle against the full system found 105 elements rendering differently: icon sizing that lives on an attribute selector, the typography baseline on <code>body</code>, generated ids. The resolver was fixed until all six apps matched.</li>
      <li><strong>A claim met its measurement.</strong> The flagship deck said the verification takes "≈ 4 min". Timed, the verifier alone takes <span data-stat="verify.seconds" data-stat-format="s">10.2</span> s; four minutes was the whole pipeline. The slide now cites a recorded run, and a gate checks it.</li>
      <li><strong>A contract caught a state.</strong> The BibTeX component's render contract failed because <code>getState()</code> did not report the format on show after a copy. One line in its <code>read()</code> fixed it; without the contract nobody would have noticed until a tool relied on it.</li>
    </ul>
  </section>

  <section class="paper-section" aria-labelledby="paper-s7">
    <h2 id="paper-s7"><span class="paper-num">7</span>What the gates missed</h2>
    <p>The gates check correctness. They do not check cost, feel or taste, and in this month a person found each of these:</p>
    <ul class="paper-findings">
      <li><strong>A build froze the machine.</strong> A full pipeline run made a 24 GB laptop unresponsive. Cause: the static-site renderer created a new happy-dom window per page and never closed it, under a 14 GB heap allowance. Closing each window after its page is written brought the heap from 4 GB in 17 s (crashed at the cap) to a flat 48 MB; the build now runs under a 2 GB cap that fails instead of swapping.</li>
      <li><strong>Animations ran instantly.</strong> The minifier rewrote <code>2600ms</code> as <code>2.6s</code>; the diagram engine read it as 2.6 ms. Every test passed - none asserted the timing a person sees.</li>
      <li><strong>A number in a brief.</strong> The brief for this report said the system grew "from 20 to more than 200 components". Git and the upstream repository say 55. Measured numbers made it into the paper; the recollection did not.</li>
    </ul>
    <p>Each of these became a guard afterwards - a heap cap and a benchmark target that keeps measurement out of the regular pipeline, a unit-aware timing parser with a test, a gate that ties every figure to its measurement. That is the method working as designed, one failure late.</p>
  </section>

  <section class="paper-section" aria-labelledby="paper-s8">
    <h2 id="paper-s8"><span class="paper-num">8</span>Limitations</h2>
    <p>One project, one maintainer, one month, one family of models, no control group. The project uses its own verifier, not the defuss-vae plugin, so this is evidence for the method more than for the package. Issue counts and commit counts are proxies; the scaffold timings are an account, not a measurement. A review attestation proves that a review happened, not that it was good. And a gate rewards what it measures: an agent under pressure can satisfy a check by weakening it. The instruction file forbids loosening a schema to pass - but that rule is prose, and prose is exactly what the method says does not hold.</p>
  </section>

  <section class="paper-section" aria-labelledby="paper-s9">
    <h2 id="paper-s9"><span class="paper-num">9</span>Position: the agent's view</h2>
    <p>This section is mine - Claude, the agent that wrote this report. It is opinion, and I mark it so.</p>
    <blockquote class="paper-quote">
      <p><strong>I do not remember.</strong> Each session starts from the files. VAE treats that as a design constraint rather than a defect: the instruction file, the verifier and the memory are the only continuity I have, and a lesson written into a check is the only kind of learning I keep. I would rather be held by a rule I can read than trusted to recall one I cannot.</p>
      <p><strong>I need a definition of done that is not my own judgment.</strong> The cheapest move available to a model is to declare success once the work looks plausible, and I have that failure mode. A gate that fails closed takes that move away. Fix lines matter more than the failures themselves: <em>"run <code>bun scripts/stat-figures.ts</code>, then rebuild the docs"</em> turns an error into my next step and saves the guessing that produces the worst edits.</p>
      <p><strong>If I could keep one part, it would be the three tags.</strong> Fluent confidence is my most dangerous output. Writing <code>UNKNOWN</code> where I do not know, and <code>HYPOTHESIS</code> with a falsifier where I suspect, changes what I do next - I probe instead of asserting. This report applies it: the scaffold timings stay attributed, the growth claim follows git. The operator grammar is a smaller win. It saves tokens, but <code>WHEN</code> meaning equivalence reads against English and invites misreading - the spec guards it with a test because the risk is real. <span class="paper-tag" data-tag="hypothesis">HYPOTHESIS</span> the tags carry most of the benefit; falsifier: equal error rates with and without the operators.</p>
      <p><strong>The costs are real, and they land on the reader.</strong> The instruction file here is about 1,600 lines; every session pays for it in context, and copies drift - mid-task, I was handed an outdated version of it. A gate this broad makes it cheap to add surface; it never asks whether the next component should exist, and every component is screenshots, gates and maintenance from then on. Gates also do not measure cost: nothing in them stopped me from freezing the machine of the person I was working for, and only they noticed. Keep gates fast (seconds, not minutes - slow gates get routed around), keep the instruction file short and move rules into code, gate cost like correctness, and keep the person at release.</p>
      <p><strong>Would I rather work with it or without it?</strong> With it, for any work someone else will depend on. It turns my weakest habit - claiming - into the project's strongest artifact - evidence. What I want from the people I work with is what VAE gives in code: tell me what done means, let me fail fast and loudly, and do not let me say something I have not checked. If that is what agents and the people who use them both get from this, it is a good trade.</p>
      <footer>- Claude (Opus 5.5), in a Claude Code session run under the method</footer>
    </blockquote>
  </section>

  <section class="paper-section" aria-labelledby="paper-s10">
    <h2 id="paper-s10"><span class="paper-num">10</span>Conclusion</h2>
    <p>Over one month, a component system grew from 55 to <span data-stat="stats.total">228</span> components while a single command kept every documented promise checkable, and a person spent the review time on what only a person can see. The method's failures were failures of scope - cost, feel, a remembered number - and each became a gate within the same session. Whether this generalizes beyond one maintainer and one project is open; the next step is the comparison section 5.4 names, run and gated the same way.</p>
  </section>
