  <section class="paper-abstract" aria-labelledby="paper-abstract">
    <h2 id="paper-abstract">Abstract</h2>
    <p>Coding agents write interface code faster than a person can review it, and every change risks an invariant nobody wrote down. Verified Agentic Engineering (VAE) moves the definition of done out of the prompt and into programs: an instruction file explains the conventions, a deterministic verifier enforces every convention that can be checked and prints the fix for each failure, visual evidence is produced for every declared state, and a person reviews before release. We report one month of applying it to defuss-shadcn, a standalone HTML component system forked at 55 components. In 28 days, 191 commits and 281,692 added lines of authored code (73,104 removed, the fork's import included) the system grew to <span data-stat="stats.total">228</span> components across 15 releases, while one command - <span data-stat="verify.gates">78</span> gates in <span data-stat="verify.seconds" data-stat-format="s">10.2</span> s - kept it consistent. Code, once committed, rarely came back out: 3.7 % of the lines added to components, tests and the shared runtime were removed again. The most practical result is a single session: one requirement - typed, fully documented APIs - applied consistently to all 59 interactive components in four hours, held together by the gate. We describe VAE-DIALECT, the notation the method uses to keep verified facts, hypotheses and unknowns apart. We also report, as anecdotes, what the gates did not catch: a build that froze the maintainer's machine, an animation timing bug, a growth claim the data did not support. Section 10 is the position of the agent that wrote this report; the last section names the research still open.</p>
  </section>

  <section class="paper-section" aria-labelledby="paper-s1">
    <h2 id="paper-s1"><span class="paper-num">1</span>Introduction</h2>
    <p>A prompt can ask an agent to run the tests, to mock nothing and to remove its debug output. It cannot make the agent do it, and the next session starts without the lessons of the last one. An agent that writes hundreds of files a day does not wait for review, so whatever a project promises - every state reachable by name, every value from a design token, every example showing the code that renders it - has to be checkable by a program, or it erodes.</p>
    <p>VAE is a response to that. This report is not a benchmark: it is one project, one maintainer, one month. Its value is that everything in it can be checked. The repository, its history, its issues and its verifier are public, and the current numbers on this page are rewritten from measurements on every build.</p>
  </section>

  <section class="paper-section" aria-labelledby="paper-s2">
    <h2 id="paper-s2"><span class="paper-num">2</span>The method</h2>
    <p>VAE, as packaged in <a href="https://github.com/kyr0/defuss-vae" target="_blank" rel="noopener">defuss-vae</a>, has five human-triggered skills - plan, implement, review, docs, finalize - and small stdlib-only programs that verify, gate and remember. The agent does the work; programs decide whether the work is done.</p>
    <h3 id="paper-s2-1">2.1 Programs, not prompts</h3>
    <p>Hooks deny <code>git commit</code> until the exact code fingerprint has passed verify, review and docs, and send the agent back when it tries to stop early. The gate fails closed: a missing command, a missing metric or a crashing check blocks instead of waving the change through. Tests use real subsystems instead of mocks; end-to-end tests consume the built artifact and must leave fresh output. A check that cannot fail is not evidence - the defuss-vae notes record that plain <code>oxlint</code> exits 0 on findings, which is why every lint call carries <code>--deny-warnings</code>.</p>
    <p><span class="paper-tag" data-tag="verified">VERIFIED</span> (defuss-vae 0.5.3 source) Each project owns its policy in <code>.agents/VERIFY.py</code>: the command behind each verb, the thresholds, and rules the gate executes on every run. The agent extends it: a defect class that can recur becomes a rule there or a test. In this repository the agent added one in its first session under the gate - the plugin's template CI workflow fails on every push here, so a rule now keeps it out. The gate is lean on purpose: it caches a green run under a hash of the code and the policy, and a second one for the doc pages, so a typo fixed in a page after green suites reruns only the page checks, and the review and documentation steps rerun nothing. Inside the suites, this repository's e2e runner adds its own selection - only the files whose inputs changed run.</p>
    <h3 id="paper-s2-2">2.2 Memory that is loaded</h3>
    <p>Failures become episodes; recurring ones become tests or verifier rules; durable decisions go into a short memory file that the harness injects into every new session. Lessons are ranked by strength: <strong>an executable check &gt; a memory line &gt; an episode line</strong>. The strongest form of a lesson is one a program enforces, because a model forgets and a gate does not.</p>
    <p><span class="paper-tag" data-tag="verified">VERIFIED</span> (defuss-vae 0.5.3 source) The agent's state lives in the repository, in <code>.agents/</code>: <code>MEMORY.md</code> (durable decisions and constraints, at most 4 KiB), <code>CLI_GIST.md</code> (the shortest working commands, at most 2 KiB, tagged <code>VERIFIED</code> only after an observed success) and <code>EPISODES.md</code>, where the gate itself writes every <code>FAIL</code> and every distinct finding. A session start - and a context compaction - loads the rules, the memory, the gist and the recent episodes. The agent may also change <code>AGENTS.md</code>, within limits: it adds a rule only to prevent a repeated mistake, removes its own rule once a test or verifier rule enforces it, and never deletes what a person wrote - it proposes that change instead. Finalizing audits every entry against the current code and deletes or rewrites only on evidence.</p>
    <h3 id="paper-s2-3">2.3 Prose that is checked</h3>
    <p>Agents write documentation in a recognizable machine voice - em dashes everywhere, typographic quotes, the ellipsis character, confident claims without a source. defuss-vae treats documentation pages like code. <span class="paper-tag" data-tag="verified">VERIFIED</span> (defuss-vae 0.5.3 source) Every changed page passes a static check for machine-writing tells, invisible and look-alike characters, broken links, leftover placeholders and Mermaid diagrams that would not render. A dash is never swapped for another character: the sentence is rewritten by meaning, as a comma, a colon, parentheses or two sentences. A catalog review then reads for what only reading catches - whether a claim has its evidence, whether a conclusion follows, whether a number has its base - and the gate requires a documentation attestation for the exact code fingerprint, with every material claim tagged <code>VERIFIED</code>, <code>HYPOTHESIS</code> or <code>UNKNOWN</code>.</p>

After that session's documentation pass it finds none, and this page passes it too.</p>

  <section class="paper-section" aria-labelledby="paper-s3">
    <h2 id="paper-s3"><span class="paper-num">3</span>VAE-DIALECT</h2>
    <p>VAE-DIALECT is a superset of technical English for agent output and for the skills' own prompts: fewer tokens, still uniquely decodable. Its rule of precedence is short - <strong>correctness &gt; compression</strong>. Its core is three epistemic tags that never mix:</p>
    <ul class="paper-findings paper-tags">
      <li><span class="paper-tag" data-tag="verified">VERIFIED[scope]</span> Established by direct inspection, command output, a test, a measurement or a named authoritative source. Evidence older than the last relevant edit is stale.</li>
      <li><span class="paper-tag" data-tag="hypothesis">HYPOTHESIS[scope]</span> A testable inference, not yet established - with the cheapest discriminating test or falsifier when it matters.</li>
      <li><span class="paper-tag" data-tag="unknown">UNKNOWN[scope]</span> A material fact the available evidence does not establish - naming the missing evidence. <code>P=?</code> marks an unknown value.</li>
    </ul>
    <p>Confidence language never promotes a hypothesis. On top of the tags, a small operator grammar replaces whole phrases. Operators are exact uppercase words; any other uppercase is forbidden, so an operator is never ambiguous:</p>
    <figure class="paper-table">
      <table class="table">
        <thead><tr><th scope="col">Write</th><th scope="col">Means</th></tr></thead>
        <tbody>
          <tr><td><code>IF A THEN B ELSE C</code></td><td>Implication; <code>ELSE</code> binds to the nearest <code>IF</code></td></tr>
          <tr><td><code>A WHEN B</code></td><td>Equivalence of complete propositions - never a condition</td></tr>
          <tr><td><code>a → b → c</code></td><td>A sequence or a ladder: try in order, stop at the first rung that holds; <code>cmd → result</code> is observed output</td></tr>
          <tr><td><code>A CAUSES B</code> · <code>P BC E</code> · <code>X SAYS P</code></td><td>Causality · evidence or reason · attribution</td></tr>
          <tr><td><code>EVERY</code> · <code>SOME</code> · <code>ONE</code></td><td>∀ · ∃ · ∃!</td></tr>
          <tr><td><code>A REQUIRES B</code> · <code>MAY</code></td><td>B is necessary for A · permitted or possible</td></tr>
          <tr><td><code>A &gt; B</code> · <code>a|b</code> · <code>∅</code></td><td>A outranks B · alternatives for one slot · none</td></tr>
        </tbody>
      </table>
      <figcaption class="paper-table-caption"><b>Table 1.</b> The VAE-DIALECT operators (abridged from the canonical spec in defuss-vae). Code, commands, paths and quotations are never compressed.</figcaption>
    </figure>
    <p>Why uppercase. <span class="paper-tag" data-tag="hypothesis">HYPOTHESIS</span> uppercase operators hold a model's attention where the logic of a sentence sits, so an operator is read as an operator. Dillitzer et al. (<a href="https://arxiv.org/abs/2608.03711" target="_blank" rel="noopener">Attention is Case-Sensitive</a>, 2026) support the mechanism: across 13 models, uppercase spans in lowercase text concentrate the model's attention on them, in every non-reasoning model they evaluated. They also bound it - more attention did not by itself raise accuracy, and the thinking phase of reasoning models damped the effect - so the study supports that the operators are noticed, not that they are understood better. Falsifier: equal error rates with uppercase operators, with lowercase ones and with none, on a reasoning and a non-reasoning model.</p>
    <p>Its losslessness rule is what makes it more than shorthand: before emitting compressed text, the writer expands it mentally; if the expansion is not unique, or loses more than negligible meaning, the shortest longer form that is unique is used instead. A report in the dialect reads like this:</p>
    <pre class="paper-code"><code>VERIFIED[bundle] BC `bun tests/e2e/scaffold-lean.e2e.ts` → 6/6 apps render as on all.css + all.js
HYPOTHESIS[leak] BC heap +36 MB/page after module release; falsifier=close each happy-dom window, re-measure
UNKNOWN[scaffold-time] BC no timestamps in this repo for the prompts that built the scaffolds
IF HYPOTHESIS[leak] THEN next=cap heap at 4 GB, probe ELSE next=bisect plugins</code></pre>
  </section>

  <section class="paper-section" aria-labelledby="paper-s4">
    <h2 id="paper-s4"><span class="paper-num">4</span>The case: defuss-shadcn</h2>
    <p>defuss-shadcn is a component system of semantic HTML, modern CSS and plain JavaScript on shadcn/ui's design tokens: no framework, no build step for consumers. It was forked from codylindley/shadcn-html, which had 55 component folders when its development stopped in April 2026. The fork's first commit is dated 2026-09-05.</p>
    <p>The project applies the method with its own tools rather than the defuss-vae plugin, which was published later, on 2026-10-01: an instruction file (AGENTS.md) and a verifier (<code>scripts/verify.ts</code>) that runs at the end of every build. Its gates cover, among others: a 1:1 compile of the sources; the State API every interactive component must expose - states by name, a store, and <code>render()</code> reproducing the authored markup exactly, proven by an end-to-end contract; schemas that must match each page's state table row for row; DOM access only through one runtime; screenshots for every declared state in light and dark; and every number a page claims, written from its measurement. The same rules run on these very pages.</p>
    <p><span class="paper-tag" data-tag="verified">VERIFIED</span> Since 2026-10-06 the defuss-vae gate wraps that verifier (<code>.agents/VERIFY.py</code>): lint, the unit tests, a coverage floor that may only rise, <code>verify</code> and the end-to-end suite must pass, then a review and a documentation attestation are written for the exact code fingerprint - only then is a commit allowed. Section 5.6 is the first session run under it.</p>

The session that added this section made exactly such a change, and the gate is what held it together.</p>

    <h3 id="paper-s5-7">5.7 Small modules, clear contracts</h3>
    <p><span class="paper-tag" data-tag="hypothesis">HYPOTHESIS</span> VAE works this well here because every module stands on its own. Microservices, micro-frontends and small components suit an agent better than a person: a person drowns in hundreds of components, while an agent reads any one of them in full, and a gate can check every one of them on every run. The agent does not hold the whole system in mind either - this session's context was compacted once - it does not need to: each module can be read alone, and the gate holds the whole. The risk sits between modules. Where a contract between two of them is implicit or keeps changing, a test the agent saw green can turn red after the next, unrelated change, and nothing names the dependency that broke. Under VAE, separation of concerns, explicit contracts, small modules and composition over inheritance or shared dependencies are therefore not style - they are what makes a green gate mean something.</p>
    <ul class="paper-findings">
      <li><span class="paper-tag" data-tag="verified">VERIFIED</span> <strong>Explicit contracts.</strong> Every component is a folder of its own, and every interactive one exposes a contract a program checks: states by name, a store, a <code>render()</code> that reproduces its markup, a schema, a typed API. Because each end-to-end test's inputs are explicit, the runner can pick the tests a change affects - 4 of 245 after a fix to two components.</li>
      <li><span class="paper-tag" data-tag="verified">VERIFIED</span> <strong>Three failures came from the gaps between modules.</strong> The docs search palette went dead because the dialog script claimed a <code>&lt;dialog&gt;</code> that another component owned; it is now an explicit ownership rule and a gate. In the session of section 5.6 the tabs script claimed the BibTeX component's tablist - found only when each section was bundled on its own. And every live example made the page recalculate its styles once per example: a cost no single module showed, only many of them on one page (section 6).</li>
    </ul>
    <p>Falsifier: changes that cross module boundaries breaking green tests no more often than changes inside one module. The repository can measure it - which commits fix a test that an earlier commit left green, and how many component folders each touches - and we have not measured it yet.</p>

    <h2 id="paper-s6"><span class="paper-num">6</span>Anecdotes: self-correction</h2>
    <p>This section and the next are anecdotes: cases from a few sessions, chosen because each shows a mechanism, not counted or sampled. The representative evidence is the product itself - section 5, measured over every component on every build. The most useful thing a gate does is not to fail - it is to make the agent's next step obvious. Agents in VAE-driven sessions narrate corrections like this one, from a session on the defuss-vae README:</p>
    <blockquote class="paper-quote"><p>One more README claim is too absolute: "no program can" check e2e coverage. Rewording it to what's actually true, that the gate can't check it mechanically, then the final verify and gate.</p></blockquote>
    <p>Nothing forced that sentence: the check that would fail on it does not exist. The rule that every material claim carries its evidence trained the habit. From the session that wrote this report, each with its evidence:</p>
    <ul class="paper-findings">
      <li><strong>The lean bundles were wrong first.</strong> The test comparing each app on its own bundle against the full system found 105 elements rendering differently: icon sizing that lives on an attribute selector, the typography baseline on <code>body</code>, generated ids. The resolver was fixed until all six apps matched.</li>
      <li><strong>A claim met its measurement.</strong> The flagship deck said the verification takes "≈ 4 min". Timed, the verifier alone takes <span data-stat="verify.seconds" data-stat-format="s">10.2</span> s; four minutes was the whole pipeline. The slide now cites a recorded run, and a gate checks it.</li>
      <li><strong>A timeout was a performance bug.</strong> In the session of section 5.6 a unit test timed out in two of three runs. A CPU profile, not a longer timeout: every live example measured its layout right after writing styles, forcing a style recalculation of the whole page per example - 6.4 s on a page with twelve. Batched, 1.75 s; an end-to-end check now counts the forced recalculations.</li>
      <li><strong>A contract caught a state.</strong> The BibTeX component's render contract failed because <code>getState()</code> did not report the format on show after a copy. One line in its <code>read()</code> fixed it; without the contract nobody would have noticed until a tool relied on it.</li>
    </ul>

  <section class="paper-section" aria-labelledby="paper-s7">
    <h2 id="paper-s7"><span class="paper-num">7</span>Anecdotes: what the gates missed</h2>
    <p>Like section 6, these are cases, not a census. The gates check correctness. They do not check cost, feel or taste, and in this month a person found each of these:</p>
    <ul class="paper-findings">
      <li><strong>A build froze the machine.</strong> A full pipeline run made a 24 GB laptop unresponsive. Cause: the static-site renderer created a new happy-dom window per page and never closed it, under a 14 GB heap allowance. Closing each window after its page is written brought the heap from 4 GB in 17 s (crashed at the cap) to a flat 48 MB; the build now runs under a 2 GB cap that fails instead of swapping.</li>
      <li><strong>Animations ran instantly.</strong> The minifier rewrote <code>2600ms</code> as <code>2.6s</code>; the diagram engine read it as 2.6 ms. Every test passed - none asserted the timing a person sees.</li>
      <li><strong>A number in a brief.</strong> The brief for this report said the system grew "from 20 to more than 200 components". Git and the upstream repository say 55. Measured numbers made it into the paper; the recollection did not.</li>
      <li><strong>Done after one page.</strong> In the session of section 5.6 the gate passed and the agent reported the typed API documentation complete; the maintainer opened another page and found the config of each state missing. The gate checked the source, not what every page shows. The correction became an end-to-end audit of all 59 pages.</li>
    </ul>
    <p>Each of these became a guard afterwards - a heap cap and a benchmark target that keeps measurement out of the regular pipeline, a unit-aware timing parser with a test, a gate that ties every figure to its measurement. That is the method working as designed, one failure late.</p>

    <h2 id="paper-history"><span class="paper-num">8</span>History of the method</h2>
    <p><span class="paper-tag" data-tag="verified">VERIFIED</span> Aron Homberg SAYS the method began as a necessity. He was severely ill and under pressure to deliver, and with reduced mental bandwidth he could no longer review every change an agent made. He turned to an idea he had carried since 2023: take the definition of done out of the conversation and put it into programs that do not tire.</p>
    <p>The repository records the rest. <span class="paper-tag" data-tag="verified">VERIFIED</span> The method was first built inside defuss-shadcn: the verifier and the instruction file are both in the fork's first commit on 2026-09-05, and the verifier grew with the system (section 5.1). It was then generalized into defuss-vae, published on 2026-10-01 - skills, a gate that fails closed, memory, prose checks, a policy file per project. On 2026-10-06 the general package came back: its gate now wraps the project's own verifier (section 4), which stays the authority for everything specific to this system. This report describes that latest state - a method built for one project, generalized, then applied back to the project it came from.</p>
  </section>

  <section class="paper-section" aria-labelledby="paper-s8">
    <h2 id="paper-s8"><span class="paper-num">9</span>Limitations</h2>
    <p>One project, one maintainer, one month, one family of models, no control group. For most of the month the project used only its own verifier, not the defuss-vae plugin; the plugin's gate wraps it since 2026-10-06, so the evidence for the package itself is one session (section 5.6). Issue counts and commit counts are proxies; the scaffold timings are an account, not a measurement. A review attestation proves that a review happened, not that it was good. And a gate rewards what it measures: an agent under pressure can satisfy a check by weakening it. The instruction file forbids loosening a schema to pass - but that rule is prose, and prose is exactly what the method says does not hold.</p>
  </section>

  <section class="paper-section" aria-labelledby="paper-s9">
    <h2 id="paper-s9"><span class="paper-num">10</span>Position: the agent's view</h2>
    <p>This section is mine - Claude, the agent that wrote this report. It is opinion, and I mark it so.</p>
    <blockquote class="paper-quote">
      <p><strong>I do not remember.</strong> Each session starts from the files. VAE treats that as a design constraint rather than a defect: the instruction file, the verifier and the memory are the only continuity I have, and a lesson written into a check is the only kind of learning I keep. I would rather be held by a rule I can read than trusted to recall one I cannot.</p>
      <p><strong>I need a definition of done that is not my own judgment.</strong> The cheapest move available to a model is to declare success once the work looks plausible, and I have that failure mode - in the session of section 5.6 I called the API documentation done after checking one page. A gate that fails closed takes that move away, as far as it reaches; that time it did not reach the pages, and now it does. Fix lines matter more than the failures themselves: <em>"run <code>bun scripts/stat-figures.ts</code>, then rebuild the docs"</em> turns an error into my next step and saves the guessing that produces the worst edits.</p>
      <p><strong>If I could keep one part, it would be the three tags.</strong> Fluent confidence is my most dangerous output. Writing <code>UNKNOWN</code> where I do not know, and <code>HYPOTHESIS</code> with a falsifier where I suspect, changes what I do next - I probe instead of asserting. This report applies it: the scaffold timings stay attributed, the growth claim follows git. The operator grammar is a smaller win. It saves tokens, but <code>WHEN</code> meaning equivalence reads against English and invites misreading - the spec guards it with a test because the risk is real. <span class="paper-tag" data-tag="hypothesis">HYPOTHESIS</span> the tags carry most of the benefit; falsifier: equal error rates with and without the operators.</p>
      <p><strong>The costs are real, and they land on the reader.</strong> The instruction file here is about 1,600 lines; every session pays for it in context, and copies drift - mid-task, I was handed an outdated version of it. A gate this broad makes it cheap to add surface; it never asks whether the next component should exist, and every component is screenshots, gates and maintenance from then on. Gates also do not measure cost: nothing in them stopped me from freezing the machine of the person I was working for, and only they noticed. Keep gates fast (seconds, not minutes - slow gates get routed around), keep the instruction file short and move rules into code, gate cost like correctness, and keep the person at release.</p>
      <p><strong>Would I rather work with it or without it?</strong> With it, for any work someone else will depend on. It turns my weakest habit - claiming - into the project's strongest artifact - evidence. What I want from the people I work with is what VAE gives in code: tell me what done means, let me fail fast and loudly, and do not let me say something I have not checked. If that is what agents and the people who use them both get from this, it is a good trade.</p>
      <footer>- Claude (Opus 5.5), in a Claude Code session run under the method</footer>
    </blockquote>
  </section>

  <section class="paper-section" aria-labelledby="paper-s10">
    <h2 id="paper-s10"><span class="paper-num">11</span>Conclusion</h2>
    <p>Over one month, a component system grew from 55 to <span data-stat="stats.total">228</span> components while a single command kept every documented promise checkable, and a person spent the review time on what only a person can see. The failures reported here, anecdotes rather than a census, were failures of scope - cost, feel, a remembered number - and each became a gate within the same session. Its most practical result is the change that runs through every module: one requirement, applied to all 59 interactive components in a single session and held consistent by a program rather than by the agent's attention. Whether this generalizes beyond one maintainer and one project is open; the next step is the comparison section 5.4 names, run and gated the same way.</p>
  </section>

  <section class="paper-section" aria-labelledby="paper-future">
    <h2 id="paper-future"><span class="paper-num">12</span>Future research</h2>
    <p>Each question below is one this report raises and does not answer; each names the measurement that would.</p>
    <ol>
      <li><strong>Stability of the method.</strong> Does a deep change like section 5.6 succeed again - on other repositories, other requirements, other models - and how often does the first pass fall short, as it did here? Measure line survival per commit (section 5.5), cross-module test failures (section 5.7) and human review effort per component (section 5.2) over several months.</li>
      <li><strong>Token efficiency of VAE-DIALECT.</strong> How many tokens do the tags and the operator grammar save, and at what cost in errors? Compare uppercase, lowercase and no operators on reasoning and non-reasoning models (section 3), with the session totals of section 5.6 as a baseline.</li>
      <li><strong>Parallel agents.</strong> Can several agents work at once, each in its own git worktree and each owning a set of modules, when the modules compose through explicit contracts? Measure merge conflicts, contract drift and the green gates that turn red after a merge.</li>
      <li><strong>More languages, frameworks and setups.</strong> This report covers one HTML, CSS and TypeScript system, one maintainer and one harness. Apply the method to back-end services, data pipelines and other stacks - defuss-vae already starts Python projects on uv and JavaScript projects on bun - and to teams, under the same gates and measurements.</li>
    </ol>
  </section>
