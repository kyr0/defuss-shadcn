<H2>Semantic HTML first</H2>

<p class="text-sm text-muted-foreground mb-5">Components start from the most semantic native element available. A <code>&lt;button&gt;</code> is already a button - no <code>role="button"</code> needed. A <code>&lt;dialog&gt;</code> already traps focus and handles Escape. ARIA is only added when the native element doesn't express the full semantics of the widget.</p>

<div class="grid grid-cols-auto gap-4 mb-10">
  <CodeWindow lang="markup" title="Avoid: unnecessary ARIA" column code={"<!-- Don't add ARIA roles to native elements -->\n<div role=\"button\" tabindex=\"0\"\n  onclick=\"...\">\n  Click me\n</div>"} />
  <CodeWindow lang="markup" title="Prefer: native elements" column code={"<!-- Native button: focusable, keyboard\n     activatable, announced correctly -->\n<button class=\"btn\">\n  Click me\n</button>"} />
</div>

<H2>Roving tabindex</H2>

<p class="text-sm text-muted-foreground mb-5">Composite widgets (tabs, toolbars, menus) use roving tabindex so the entire widget acts as a single tab stop. Only one item has <code>tabindex="0"</code> at a time - all others have <code>tabindex="-1"</code>. Arrow keys move focus between items.</p>

<CodeWindow lang="html" title="roving tabindex pattern" mb="1.5rem" code={"<!-- Only the active tab is in the tab order -->\n<div role=\"tablist\">\n  <button role=\"tab\" tabindex=\"0\" aria-selected=\"true\">Tab 1</button>\n  <button role=\"tab\" tabindex=\"-1\" aria-selected=\"false\">Tab 2</button>\n  <button role=\"tab\" tabindex=\"-1\" aria-selected=\"false\">Tab 3</button>\n</div>\n\n<!-- User presses → - focus moves to Tab 2:\n     Tab 1: tabindex=\"-1\", Tab 2: tabindex=\"0\" -->"} />

<CodeWindow lang="javascript" title="roving tabindex - JavaScript pattern" mb="1.5rem" code={"// Move focus to the item at `index` - df$ writes the attributes\nfunction focusItem(items, index) {\n  df$(items).attr('tabindex', '-1');\n  df$(items[index]).attr('tabindex', '0');\n  items[index].focus(); // focus stays a native call\n}"} />

<p class="text-sm text-muted-foreground mb-5"><strong>Used by:</strong> Tabs, Toolbar, Toggle Group, Dropdown Menu, Tree View</p>

<H2>Focus management</H2>

<p class="text-sm text-muted-foreground mb-5">When overlays open and close, focus must move predictably. Dialogs trap focus. When a modal closes, focus returns to the trigger that opened it.</p>

<div class="def-grid">
  <span class="def-term">Focus trapping</span>
  <span class="text-sm text-muted-foreground"><code>&lt;dialog&gt;</code> with <code>.showModal()</code> traps focus natively - Tab cycles within the dialog only. No JS focus-trap library needed.</span>
  <span class="def-term">Focus restoration</span>
  <span class="text-sm text-muted-foreground">When a dialog or menu closes, focus returns to the trigger element that opened it. JS stores a reference to the trigger before opening.</span>
  <span class="def-term">Focus-visible</span>
  <span class="text-sm text-muted-foreground"><code>:focus-visible</code> shows focus rings only on keyboard navigation, not mouse clicks. Applied to every interactive component.</span>
</div>

<CodeWindow lang="javascript" title="focus restoration pattern" mb="2.5rem" code={"// Store the trigger before opening\ndialog._trigger = triggerButton;\ndialog.showModal();\n\n// Restore focus when the dialog closes\ndf$(dialog).on('close', () => dialog._trigger?.focus());"} />

<H2>Live regions</H2>

<p class="text-sm text-muted-foreground mb-5">Live regions announce dynamic content changes to screen readers without moving focus. Toast notifications and alerts use these to ensure users are informed of updates.</p>

<div class="def-grid">
  <code style="font-size:0.8125rem;font-weight:600;">aria-live="polite"</code>
  <span class="text-sm text-muted-foreground">Announced after the screen reader finishes its current output. Used for info and success toasts.</span>
  <code style="font-size:0.8125rem;font-weight:600;">aria-live="assertive"</code>
  <span class="text-sm text-muted-foreground">Interrupts the screen reader immediately. Used for error/destructive toasts and alerts.</span>
  <code style="font-size:0.8125rem;font-weight:600;">aria-atomic="true"</code>
  <span class="text-sm text-muted-foreground">The entire region is announced as a whole, not just the changed parts.</span>
</div>

<CodeWindow lang="markup" title="live region - toast notification" mb="2.5rem" code={"<!-- Success toast: polite announcement -->\n<div class=\"toast\" role=\"status\"\n  aria-live=\"polite\" aria-atomic=\"true\">\n  Settings saved successfully.\n</div>\n<!-- Error toast: assertive (immediate) announcement -->\n<div class=\"toast\" data-variant=\"destructive\"\n  role=\"alert\" aria-live=\"assertive\" aria-atomic=\"true\">\n  Failed to save. Please try again.\n</div>"} />

<H2>Screen reader considerations</H2>

<p class="text-sm text-muted-foreground mb-5">A few patterns help screen readers present clean, meaningful content.</p>

<div class="def-grid">
  <span class="def-term">Decorative icons</span>
  <span class="text-sm text-muted-foreground">Icons next to text labels get <code>aria-hidden="true"</code> so they're not announced redundantly.</span>
  <span class="def-term">Icon-only buttons</span>
  <span class="text-sm text-muted-foreground">Buttons with no visible text need <code>aria-label</code> to provide an accessible name: <code>&lt;button aria-label="Close"&gt;</code>.</span>
  <span class="def-term">Visually hidden text</span>
  <span class="text-sm text-muted-foreground">Text that should be announced but not visible uses the shipped <code>.sr-only</code> utility (see below).</span>
  <span class="def-term">Form labels</span>
  <span class="text-sm text-muted-foreground">Every form input has a visible <code>&lt;label&gt;</code> element with a matching <code>for</code>/<code>id</code> pair, or <code>aria-label</code> for unlabeled inputs.</span>
</div>

<CodeWindow lang="html" title="icon button accessibility" mb="2.5rem" code={"<!-- Icon-only button: needs aria-label -->\n<button class=\"btn\" data-size=\"icon\" aria-label=\"Close\">\n  <svg aria-hidden=\"true\">...</svg>\n</button>\n\n<!-- Button with text: the icon is decorative -->\n<button class=\"btn\">\n  <svg aria-hidden=\"true\">...</svg>\n  Save Changes\n</button>"} />

<H2>Screen-reader-only content</H2>

<p class="text-sm text-muted-foreground mb-5">
  Some text belongs to the accessibility tree but not to the visual design: an extra word of context on a link, the unit a <code>{"<meter>"}</code> omits, the label an icon-only control needs. <code>.sr-only</code> ships in the optional <a href="#install"><code>theme/utils/accessibility.css</code></a> module and clips content to a 1px box - CSS the browser still hands to assistive technology (unlike <code>display:none</code> or <code>visibility:hidden</code>, which hide it from screen readers too). <code>.not-sr-only</code> reverses it - the classic skip-link pattern. This very page links the module, so the demo below is the real utility, not a replica.
</p>

```html example schema="none" label="Extra context for a screen reader" hint="The link reads 'Read the changelog' on screen; a screen reader announces 'Read the changelog (opens the release history)'. The preview loads the real module - the phrase is in the accessibility tree, clipped to a 1px box."
<a class="btn" data-variant="link" href="#">Read the changelog<span class="sr-only"> (opens the release history)</span></a>
```

<p class="text-xs text-muted-foreground mt-3 mb-8">
  The link reads identically on screen - a screen reader announces the extra phrase. Never put the <em>only</em> accessible name of a focusable control inside <code>.sr-only</code>; use <code>aria-label</code> for that.
</p>
