<PageHeader slug="bundles" title="Bundles & Downloads">
  Three ways to load the system, from one file pair to one file per component: <code>all.*</code> carries every component, a <strong>section bundle</strong> carries one sidebar section - the forms, the overlays, the website blocks - and the per-component files carry exactly one. Each way loads from the jsDelivr CDN, installs with npm, or comes as a ZIP to copy into your project.
</PageHeader>

<h2 id="three-sizes" class="h2-display">Three sizes</h2>

<DocText>All three load the same component code. They differ only in how many files a page requests and how much of the system it downloads. Every way starts with <code>core.css</code> (tokens + utilities); the section and per-component ways also load <code>core.js</code> (the <code>df$</code> runtime every component binds to), which <code>all.js</code> already embeds.</DocText>

<TableCard title="Ways to load" rows={[

]} code={[1]} />

<DocText>The <DocLink href="installation.html">Installation</DocLink> page covers <code>all</code> and per-component loading; this page covers the section bundles and the downloads.</DocText>

<h2 id="section-bundles" class="h2-display">The section bundles</h2>

<DocText>Every component sits in exactly one sidebar section, and every sidebar section that holds components ships as one bundle: <code>dist/sections/&#123;section&#125;.css</code>, plus <code>.js</code> when a member has behavior, plus the minified twins and source maps. The WYSIWYG Editors section is the extra bundle <code>components/wysiwyg.*</code> that every page of this documentation loads. A section bundle holds only its own components, so loading several sections never ships a component twice.</DocText>

<DocText><strong>Needs</strong> lists the other sections whose components the section's documented markup uses: a Website pricing block is built from Buttons and Badges, a Dialog from Buttons. The list is computed from every <code>html</code> block of the members' component skills, plus the markup their JavaScript writes. Primitives appears almost everywhere because it carries Typography, the page's base text size. Sizes are minified + gzip-compressed, CSS and JS together, without core.</DocText>

<h2 id="zip" class="h2-display">Download a ZIP (vendoring)</h2>

<DocText>For a project that cannot reach a CDN or a registry - an offline build, a locked-down network, a CMS theme folder - every GitHub release attaches one ZIP per section and one for <code>all</code>. The links in the table above point at the release of this page's version. Each ZIP is complete on its own: core, every section the chosen one needs, and the section, as readable files, minified files and source maps, with the license, the third-party notice and a README that shows the load order.</DocText>

<DocText>Unzip the folder into your static files and copy the tags from its README. The <ZipLink name="all" /> ZIP holds <code>core.css</code> and <code>all.*</code> - <code>all.js</code> embeds the runtime, so it has no <code>core.js</code>. Releases up to v0.9.5 predate the split and attach no ZIPs; for the whole repository (sources, docs and all), use the source archive GitHub attaches to every release, or the <DocLink href="installation.html#toc-self-hosting">Self-hosting</DocLink> download.</DocText>

<h2 id="how" class="h2-display">How the split is made</h2>

<DocText>The sidebar is the source: <code>scripts/lib/sections.ts</code> reads it, assigns each component to the one section that links its page, and fails the build when a component is in no section or in two. <code>scripts/bundle.ts</code> builds the bundles, <code>bun run verify</code> checks that each carries exactly its members and no copy of the core runtime, and <code>dist/stats.json</code> records members, needs and sizes - this page renders from it. <code>scripts/release-zips.ts</code> packs the ZIPs from the same data when a release is cut.</DocText>
