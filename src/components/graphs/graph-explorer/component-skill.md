# Pattern: Graph Explorer

## Native basis

A `<div class="graph-explorer">` becomes one focusable `role="application"`
viewport. A Web Worker started from the component's own source owns the graph:
the hierarchy of clusters, the layouts, the cycles and every dot and bulk edge,
drawn into an `OffscreenCanvas` and handed over as an `ImageBitmap`. The main
thread keeps a bounded pool of DOM slots - chips and cards for the nodes worth
reading, labels along the edges - and morphs them only when their markup
changes. The rest of an explorer's interface (breadcrumb, search, outline,
details, relations, a layer switch) are **outlets**: elements the page places
where it likes - typically Panels of a Border Layout - that the runtime fills.

## Native Web APIs

- [Web Workers](https://developer.mozilla.org/en-US/docs/Web/API/Web_Workers_API) + [`Blob` URLs](https://developer.mozilla.org/en-US/docs/Web/API/URL/createObjectURL_static) - the graph lives off the main thread; a classic Blob worker also starts inside an opaque-origin sandbox
- [`OffscreenCanvas`](https://developer.mozilla.org/en-US/docs/Web/API/OffscreenCanvas) + [`ImageBitmapRenderingContext`](https://developer.mozilla.org/en-US/docs/Web/API/ImageBitmapRenderingContext) - the worker draws the far field; the bitmap moves to the page without a copy
- [Transferable objects](https://developer.mozilla.org/en-US/docs/Web/API/Web_Workers_API/Transferable_objects) - bitmaps and tier arrays cross threads for free
- [`requestAnimationFrame()`](https://developer.mozilla.org/en-US/docs/Web/API/Window/requestAnimationFrame) - one clock for the bitmap and the DOM writes
- [Pointer Events](https://developer.mozilla.org/en-US/docs/Web/API/Pointer_events) + [`setPointerCapture()`](https://developer.mozilla.org/en-US/docs/Web/API/Element/setPointerCapture) - pan, pinch, press and hold
- [`wheel`](https://developer.mozilla.org/en-US/docs/Web/API/Element/wheel_event) - zoom anchored at the cursor
- [Popover API](https://developer.mozilla.org/en-US/docs/Web/API/Popover_API) - the keyboard map
- [`ResizeObserver`](https://developer.mozilla.org/en-US/docs/Web/API/ResizeObserver) + [`MutationObserver`](https://developer.mozilla.org/en-US/docs/Web/API/MutationObserver) - the viewport refits; attributes written from outside apply at once
- [`translate`](https://developer.mozilla.org/en-US/docs/Web/CSS/translate) + [`contain`](https://developer.mozilla.org/en-US/docs/Web/CSS/contain) - slots move on the compositor, the viewport's layout stays its own
- [CSS masks](https://developer.mozilla.org/en-US/docs/Web/CSS/mask) - the icons: one empty element each, painted in the current color
- [Relative colors](https://developer.mozilla.org/en-US/docs/Web/CSS/CSS_colors/Relative_colors) + [`color-mix()`](https://developer.mozilla.org/en-US/docs/Web/CSS/color_value/color-mix) - type colors and tints from the theme's chart tokens
- [`@starting-style`](https://developer.mozilla.org/en-US/docs/Web/CSS/@starting-style) - nodes fade in as they get DOM
- [WAI-ARIA combobox pattern](https://www.w3.org/WAI/ARIA/apg/patterns/combobox/) - the search outlet; the outline is a [tree](https://www.w3.org/WAI/ARIA/apg/patterns/treeview/)
- [`prefers-reduced-motion`](https://developer.mozilla.org/en-US/docs/Web/CSS/@media/prefers-reduced-motion) / [`prefers-contrast`](https://developer.mozilla.org/en-US/docs/Web/CSS/@media/prefers-contrast) / [`forced-colors`](https://developer.mozilla.org/en-US/docs/Web/CSS/@media/forced-colors) - jumps instead of flights, stronger strokes, system colors (also on the canvas)

## Structure

```html
<div class="graph-explorer" id="kg" data-nodes="100000" data-seed="7" data-frame aria-label="Service graph"></div>
```

- `data-nodes` - the size of the synthetic graph, 2,000 to 4,000,000 (default
  `1000000`); `data-seed` - its seed (default `7`): the same seed builds the same
  graph, so ids are stable across loads.
- `data-source="external"` - no synthetic graph: the explorer waits for the
  page's own (`load()`, see "Your own graph").
- Ids name nodes: `c<number>` a cluster (`c0` is the top), `n<number>` an entity.
- `data-selected="c4 c9"` - the selected nodes; `data-selected-edge="c4>c9"` -
  the selected link (`<source id>><target id>`, two nodes of the view; nodes and
  a link are never selected together); `data-focus="c12"` - the cluster the view
  is in; `data-layers="nodes relations health"` - the layers shown (absent: the
  base layers `nodes relations`; empty: none); `data-compact` - every node a
  one-line chip; `data-expanded` - the selection's full page in the details
  outlet. These are the state.
- `data-hud` - a performance overlay (nodes, DOM, canvas, worker timing).
- `data-frame` - a border and radius when it stands alone (in a Panel the panel
  is the frame).
- Its height: `100%` of its container, at least `--graph-explorer-min-height`
  (default `20rem`); a Panel body that holds it gives it all its room.

### Outlets and outputs

Anything the page binds with `data-graph-explorer-for="<id>"` - the element
itself or one inside it:

| Attribute | The runtime puts in it |
| --- | --- |
| `data-graph-explorer-outlet="breadcrumb"` | a Breadcrumb of the path to the view; a crumb moves up |
| `data-graph-explorer-outlet="search"` | a search combobox over every node (the scan runs in the worker); a result flies there |
| `data-graph-explorer-outlet="outline"` | a filterable tree of the view's children (the biggest first) |
| `data-graph-explorer-outlet="details"` | the detail renderer's view of the first selected node or of the selected link; expanded, its full page |
| `data-graph-explorer-outlet="relations"` | a Table of its relations, each link drawn by the edge label renderers (a click on one inspects it); for a link, its single links |
| `data-graph-explorer-outlet="layers"` | the layer switch: a Toggle Group of the layers (Nodes, Relations, Labels, Health, the plugins'), each with its colour as an Indicator dot, and Compact after a Separator |
| `data-graph-explorer-outlet="updates"` | Updates: every change of the shown layers, newest first, one compact row each in a Virtual List (a plain list of the newest 200 without `df$.shadcn.virtualList`); a row selects its node or link |
| `data-graph-explorer-output="details-title"` | the details title (the authored text while nothing is selected) |
| `data-graph-explorer-output="relations-title"` | the selected node's name and its relation count ("Identity · 5"), for a link the names of both ends and its count (the authored text while nothing is selected); the label beside it is the page's |
| `data-graph-explorer-output="view"` | the view's name |
| `data-graph-explorer-output="status"` | the announcements (the explorer's own live region when there is none) |
| `data-graph-explorer-action="up"` / `fit` / `live` / `help` / `collapse` | move up, fit, Live mode on / off (`aria-pressed`), the keyboard map, back from an expanded page |

Inside the explorer, renderers write `data-graph-explorer-action="enter"` /
`bring` / `expand` / `collapse` / `details` (acting on their node or the
selected link), `data-graph-explorer-goto="<id>"` (fly there - on an expanded
page: that node's page, so a page drills down into the next) and
`data-graph-explorer-edge="<source id>><target id>"` (select that link).

A click on a link - its label or its line - selects it: the rest of the graph
steps back and the details show its traffic both ways, the relations it carries,
the circuit breakers it bundles, who sends and who receives most; `E` or a
double click expands it, `Esc` lets it go.

Expand maximizes the **Panel** that holds the details outlet (and restores it
on the way back); a Panel holding the relations outlet renders it when it
unfolds. The whole application - toolbar north, outline west, the graph in the
center, details east, relations south - is a Border Layout of Panels on the
page:

### Plugins

`df$.shadcn.graphExplorer.register(scope, plugin)` - `scope` is `'global'` or one
explorer (its plugins win). A renderer is a pure function of its input that
returns `ctx.html` markup (every interpolation escaped; `on*` attributes, URLs
that run code and active elements are stripped):

- **node** - `match(node)` returns a score or `false`, `sizes: { chip, card }`
  (or a function of the node), `render(node, ctx)` per tier (`ctx.tier` is
  `chip` or `card`). Without `layer` it draws the node itself (the nodes
  layer) and puts `ctx.parts` - the other layers' parts - where they belong (the
  runtime appends them when it leaves them out). With `layer` it draws that
  layer's **part** of a node: a chip part adds its width, a card part its height;
  `layerLabel`, `layerIcon` and `layerColor` name a layer of its own in the
  switch.
- **edge** - `layer` (default: `relations` for its rules, `labels` for its
  label); `rules`: plain data the worker evaluates for every link it draws
  (`{ when: [{ field: 'breaker.state', equals: 'open' }], style: { tone: 'danger', width: 2, gap: true } }`);
  `label`: DOM labels along links in three tiers (`icon`, `label`, `full`)
  picked by the link's length on screen, budgeted, never overlapping;
  `detail`: `{ match(item), title(item), render(item, ctx) }` - the details of a
  selected link (`item.source`, `item.target`, `item.edge`; its numbers from
  `ctx.fetchEdge(item.id)`).
- **detail** - `render(node, ctx)` for the details outlet; `ctx.expanded` asks
  for the node's full page. Anything async goes through `ctx.request(key, load)`,
  which renders the node again when the value arrives. `page(node)` returning
  false says a node has no page; `ctx.expandable` is true only where a page can
  show (a details outlet, and a renderer that offers one) - an Expand button
  belongs only there (an edge `detail` takes `page(item)` the same way).
- **update** - `update: { match(update), render(update, ctx) }`: one row of the
  Updates outlet (`ctx.html`, `ctx.icon`, `ctx.color(layer)`, `ctx.time(ms)`);
  the explorer wraps it in the button that selects the update's node or link.
  Keep it to one line - the rows are 2rem high.

The details are markup the runtime morphs on every change. A library component
with a script inside them - a Chart, a Geo Map, an Avatar - goes in
`ctx.island(key, markup)`: an island keeps its element, and what its script
made, while its key and its markup stay the same. `ctx.island(key, markup, mount)`
also runs `mount(el)` once when the island's element is made - bind a Data Grid's
records or a chart's data there - and the function it returns when the island
goes. `ctx.fetchRows(id)` answers every row behind a node or a link, built by
the worker: the entities below a cluster (id, label, type, system, domain,
owner, out, in, rows, freshness) or a link's single links both ways (from, to,
relation, direction, the systems).

```html
<!-- a detail renderer's markup: CSS-only components inline, a Chart in an island -->
<dl class="graph-explorer-stats"><div class="graph-explorer-stat"><dt>p95</dt><dd>63 ms</dd></div></dl>
<div class="graph-explorer-island" data-graph-explorer-island="latency:c26">
  <div class="chart" data-size="sm" role="img" aria-label="p95 latency" data-chart='{"xAxis":{"type":"category","data":["0h","1h","2h"]},"yAxis":{"type":"value"},"series":[{"type":"line","data":[61,63,58]}]}'></div>
</div>
```

The built-in plugins draw clusters and entities and their parts in four layers,
relation labels, circuit breakers (one per link
between entities, health by share on links between clusters) and the details of
a node and of a link - side and expanded - from the library's Badge, Button,
Card, Statistic, Table and Data Grid and the explorer's own parts. An expanded
cluster page holds every entity below it in a Data Grid, an expanded link page
every single link both ways; beside the grid, dataview aggregations of the
grid's own source show how the rows its filters match split up (by type, owner,
the largest systems; by relation, way, the busiest senders) and follow every
filter; a name in the grid opens its page. Without `df$.shadcn.dataGrid` loaded
the pages keep sample tables. The explorer's parts (`graph-explorer-stats`,
`-section`, `-rows` / `-row`, `-bar`, `-shares`, `-trail`, `-page`,
`-kpis`, `-page-grid`, `-records`), which plugins use the same way.
The icons are `ctx.icon(name)` - a Lucide subset as CSS masks;
`registerIcon(name, shapes)` adds one.

### Layers

What the graph shows is layers of information, each a filter of its own, each
drawn in its colour - the theme's chart colours in order (chart-1 turned around
the hue circle when the theme's five are one hue, as the default theme's blues):

| Layer | Shows | Default |
| --- | --- | --- |
| `nodes` | the chips and cards with each node's type, name and Expand (a cluster card zooms in), the names beside small nodes | shown |
| `relations` | the lines between nodes and their arrows, the signposts to nodes off screen; a part with a node's links and the small cycle it is in | shown |
| `labels` | the link labels (counts, relation names); a part with what a node is and how big | hidden |
| `health` | the circuit breakers: their line colours and badges; a part with a cluster's links by breaker state, an entity's freshness | hidden |
| a plugin's | its parts and its link rules and labels | hidden |

With none shown the clusters' circles and the entities' dots remain. A part is
bordered and tinted in its layer's colour (a band in a card, a pill in a chip),
an edge label in its plugin's layer's colour, a calm line in the relations
colour, a chip or a card in the nodes colour. `1`-`9` show or hide a layer.

### Live mode and updates

An update is one change: a node (`target` its id) or a link (`target`
`'<from>><to>'`, `view` the cluster whose children it joins), with the layer
it belongs to, a `type` word, a line of `text`, the target's `label`, a
`tone`. For eight seconds a changed node carries a glowing dot at its top right
and a changed link lights up in its layer's colour and fades - while that layer
is shown (a link of the health layer lights up without the relations layer).
Every update joins the `updates` outlet, newest first (the last 10,000); the
list shows the shown layers' updates only, and a reader scrolled down keeps the
rows they read.

```html
<button class="btn" data-variant="outline" data-size="sm" aria-pressed="false"
        data-graph-explorer-for="kg" data-graph-explorer-action="live">Live mode</button>
<section class="card panel" aria-labelledby="t-updates">
  <header class="panel-header"><h3 class="panel-title" id="t-updates">Updates</h3></header>
  <div class="panel-body" data-flush data-graph-explorer-for="kg" data-graph-explorer-outlet="updates"></div>
</section>
```

The `live` action (or `simulate(target, on)`) starts Live mode, the
explorer's simulation: breakers trip, probe and close (health), nodes deploy
(nodes), a link's traffic moves (relations), counts change (labels). An app
adds its own changes with `df$.shadcn.graphExplorer.update(target, update)`;
each fires `graph-explorer-update`.

### Your own graph

`df$.shadcn.graphExplorer.load(target, data)` shows a graph of the page's (a
`GraphExplorerData`) in place of the one shown; with `data-source="external"`
nothing is generated before it. The typed arrays' buffers are transferred to
the worker, refused or not (they are empty on the page afterwards; a retry
builds them anew), the label and ref lists copied:

```js
await df$.shadcn.graphExplorer.load('#kg', {
  // cluster 0 is the root; BFS order, each cluster's children side by side (parent never decreases)
  clusters: { parent: Int32Array.of(-1, 0, 0), type: Uint8Array.of(0, 1, 1), label: ['All', 'api', 'web'] },
  // sorted by cluster; ref is the page's own id (GraphNode.ref, search hits, subtree rows)
  nodes: { cluster: Int32Array.of(1, 1, 2), type: Uint8Array.of(0, 0, 1), label: ['get', 'put', 'page'], ref: ['a', 'b', 'c'] },
  // an out-CSR: node i links to target[start[i]] up to start[i + 1]
  edges: { start: Int32Array.of(0, 1, 2, 3), target: Int32Array.of(1, 2, 0), type: Uint8Array.of(0, 0, 0) },
  types: { cluster: ['Graph', 'Service'], node: ['endpoint', 'page'], edge: ['calls'] },
});
```

- A cluster holds clusters or nodes, never both and never none, and at most
  1,024 of them; the depth varies up to 256 cluster levels (a cluster whose
  children are nodes is a leaf view at any level). A view lays out its
  children in time that grows with the square of their number, so split a
  bigger cluster into groups.
- The worker checks the whole graph first - lengths, index ranges, the BFS
  order, the CSR, every type index, the bounds - and refuses it with
  `graph-explorer-error` (`Invalid graph data: ` and the first thing wrong);
  the graph shown stays. An array backed by a `SharedArrayBuffer` is refused:
  the page could change it after the check.
- An accepted graph shows at its top, nothing selected, without the old graph's
  updates, search query or outline filter; `load()` resolves `true` then
  (`false` when refused, or when a later `load()` superseded it before it
  showed). Move the view after it resolves.
- Type names come from `types`, labels from the lists; per-view cycles,
  aggregate links between clusters, search, `subtree()` and the details work as
  for a generated graph. Health, the circuit breakers, Live mode and the
  generated owner, rows and freshness are a generated graph's only
  (`ctx.synthetic` tells a renderer which it draws); changes come through
  `update()`.

## Notes

- The page never holds more than a bounded set of nodes: at most 120 cards, 300
  chips and 200 edge labels, however large the graph.
- Without `data-source="external"` the data is a synthetic service graph the
  worker builds from the seed - domains, systems (API, Worker, Store, Stream) and
  entities (Dataset, Endpoint, Document, Person, Job, Topic), linked by calls,
  reads and owns, with cycles and circuit breakers. The renderers, the outlets and
  the State API do not depend on it: `load()` replaces it with the page's graph.
- Zooming into a cluster until it fills most of the viewport enters it; zooming
  out, or panning off its disk, moves up. Search, the breadcrumb, the outline and
  the relations fly there with a smooth zoom-pan (a jump under reduced motion).
- The names the worker draws beside small nodes are measured, and the edge
  labels keep clear of them.
- Expand shows only where a page can show: an explorer without a details outlet
  draws its cards without the Expand button, and E or `expanded: true` only
  select (the state lands unexpanded).
- The canvas, the slots, the labels and every outlet's content are the runtime's
  (`data-ce-chrome`): render() and the HTML Preview Editor see only the
  element's attributes and the outlets as authored.
- Theme changes re-read the colors for the canvas; forced colors draw it in
  system colors.

## States

| State | Meaning |
| --- | --- |
| `default` | The top level, nothing selected |
| `selected` | `config.selected` nodes - or the link `config.edge` - picked at the top level (an id deeper down flies there - the state lands in `focused`) |
| `focused` | Inside the cluster `config.focus`, with or without a selection there |

```js
const graph = document.querySelector('#kg');
await graph.api.settled();                                   // the worker built the graph
await graph.api.setState('focused', { focus: 'c3' });        // enter cluster c3
await graph.api.setState('focused', { focus: 'c3', selected: ['c41'], expanded: true }); // its child's full page
await graph.api.setState('selected', { edge: 'c3>c7' });     // the link between two domains
graph.api.setState('default', { layers: ['nodes', 'relations', 'health'] }); // back to the top, health shown
graph.api.getState(); // { name: 'default', config: { focus: null, selected: [], layers: ['nodes', 'relations', 'health'], compact: false, expanded: false, edge: null } }
```

The registry global is `df$.shadcn.graphExplorerApi` /
`df$.shadcn.graphExplorerStates`; the explorer API is `df$.shadcn.graphExplorer`.
